# คู่มือผู้เล่น Mission Control Game

> คู่มือนี้เขียนสำหรับผู้เล่นโดยเฉพาะ จึงอธิบายวิธีใช้ระบบและหลักคิดในการทำงาน โดยไม่เปิดเผยคำตอบของ Sponsor เหตุการณ์ที่ยังไม่เกิด หรือแนวทางให้คะแนนของ Facilitator

## 1. เกมนี้คืออะไร

Mission Control Game คือเกมจำลองการบริหารโครงการภายใต้เวลา งบประมาณ คน และข้อมูลที่จำกัด ทีมของคุณต้องวางแผนงาน Innovation Day ให้พร้อมภายใน 10 วันทำการ

ข้อมูลตั้งต้นที่ทีมได้รับคือ:

- ผู้เข้าร่วมประมาณ 150 คน
- มีผู้บริหารระดับสูงเข้าร่วม
- งบประมาณตั้งต้นไม่เกิน 120,000 บาท
- วันจัดงานคือ Day 10

เป้าหมายของเกมไม่ใช่เพียง “ใส่ทุกงานลงตารางให้ครบ” แต่คือการแสดงให้เห็นว่าทีมสามารถ:

- ทำความเข้าใจผลลัพธ์ที่ Sponsor ต้องการ
- แยกข้อเท็จจริงออกจากสมมติฐาน
- เลือกสิ่งที่สำคัญจริง
- วางแผนโดยเคารพ Capacity และ Dependency
- ใช้งบประมาณอย่างมีเหตุผล
- ตรวจจับความเสี่ยงและสื่อสารได้เร็ว
- ปรับแผนเมื่อสถานการณ์เปลี่ยน

วงจรหลักของเกมคือ:

`Clarify → Define → Prioritize → Plan → Allocate → Execute → Track → Communicate → Adapt`

## 2. เตรียมทีมก่อนเริ่ม

### จำนวนผู้เล่น

แนะนำ 4–6 คนต่อทีม และใช้หน้าจอ Player ร่วมกันหนึ่งหน้าจอ เพื่อให้การตัดสินใจเกิดจากการสนทนาของทีมจริง

### บทบาทที่แนะนำ

ไม่จำเป็นต้องใช้ทุกบทบาท แต่การแบ่งหน้าที่จะช่วยให้เล่นได้คล่องขึ้น

- **Project Lead** ดูเป้าหมาย ภาพรวม และเป็นผู้สรุปการตัดสินใจ
- **Planner** ดู Task, Dependency, Timeline และ Capacity
- **Budget Owner** ดูค่า Task, Vendor, วงเงิน และเงินคงเหลือ
- **Risk Owner** มองหาความเสี่ยง ผลกระทบ และแผนสำรอง
- **Sponsor Liaison** เตรียมคำถามและบันทึกคำตอบจาก Sponsor
- **Reporter** เตรียม Status Update และ Decision Request

ถ้าทีมมีคนน้อย คนหนึ่งรับได้มากกว่าหนึ่งบทบาท

### อุปกรณ์และการเปิดหลายหน้าต่าง

- Player และ Facilitator เปิดคนละหน้าต่างหรือคนละ Browser ได้
- ข้อมูล Player กับ Facilitator บันทึกแยกกันใน Browser เครื่องนั้น
- ระบบไม่มีการ Sync แบบ Real-time ระหว่างสองหน้าต่าง การอนุมัติหรือคำตอบจึงต้องสื่อสารกันด้วยวาจาแล้วบันทึกในฝั่งที่เกี่ยวข้อง
- ถ้าทดลองหลายทีมบนเครื่องเดียว ควรใช้คนละ Browser Profile หรือคนละอุปกรณ์ เพราะ Player สองหน้าต่างบนโดเมนเดียวกันอาจใช้ข้อมูลชุดเดียวกัน

## 3. เริ่มเกมและการบันทึกข้อมูล

1. เปิดหน้า Mission Control
2. เลือก **Player**
3. ตั้งชื่อทีมในหน้า Mission
4. ระบบจะบันทึกข้อมูลลงเครื่องอัตโนมัติ เมื่อเห็นข้อความ **บันทึกในเครื่องแล้ว / Saved locally** แปลว่าข้อมูลล่าสุดถูกเก็บแล้ว

ข้อควรทราบ:

- การ Refresh หน้าโดยทั่วไปไม่ทำให้ข้อมูลหาย
- การล้างข้อมูล Browser หรือกด Reset จะทำให้ข้อมูล Player หาย
- ก่อนย้ายเครื่องหรือเปลี่ยน Browser ให้ Export ไฟล์ JSON จากหน้า Final
- ไฟล์ Export สามารถ Import เพื่อเล่นต่อหรือใช้ตรวจย้อนหลังได้

## 5. วิธีเล่นทีละหน้า

## 5.1 Mission — ทำความเข้าใจโจทย์

### สิ่งที่ต้องทำ

1. อ่าน Scenario และข้อจำกัดที่แสดงบนหน้าจอ
2. ตั้งชื่อทีม
3. ให้สมาชิกแต่ละคนพูดสั้น ๆ ว่า “คิดว่าโครงการนี้ต้องสำเร็จแบบไหน”
4. บันทึกข้อสงสัยไว้ อย่าเพิ่งเติมคำตอบเอง

### สิ่งที่ยังไม่ควรทำ

- อย่ารีบเลือก Solution ก่อนรู้ว่า Success คืออะไร
- อย่าถือว่าคำว่า “ประมาณ” หรือ “ผู้บริหารเข้าร่วม” มีความหมายเฉพาะโดยไม่ถาม
- อย่าตั้งเป้าว่า “จัดงานให้เสร็จ” เพราะยังวัดคุณภาพของผลลัพธ์ไม่ได้

### ตัวอย่างคำถามที่ควรเกิดขึ้น

- จำนวนผู้เข้าร่วมเป็นเป้าหมายประมาณการหรือเกณฑ์ขั้นต่ำ?
- งานนี้มีวัตถุประสงค์ทางธุรกิจอะไร?
- อะไรคือสิ่งที่ต้องมี และอะไรคือสิ่งที่มีก็ดี?
- งบประมาณรวมค่าอะไรบ้าง?
- มี Deadline ย่อยหรือ Approval ใดบ้าง?

## 5.2 Team — รู้จักทรัพยากร

ทีมมีคน 5 คน แต่ละคนทำงานได้สูงสุด 6 ชั่วโมงต่อวัน

| คน | จุดแข็งหลัก |
|---|---|
| May | Project, Coordination, Facilitation |
| Bank | Design, Media, Content |
| Ton | IT, Streaming, Data |
| Fon | Admin, Procurement, Logistics |
| Ploy | Communication, Registration, Content |

### วิธีใช้ข้อมูลทักษะ

- ทักษะเป็นคำแนะนำเรื่องความเหมาะสม ไม่ใช่ข้อห้ามตายตัว
- งานหนึ่งแบ่งให้หลายคนหรือหลายวันได้
- ใช้คนที่ถนัดมักลดความเสี่ยง แต่บางครั้งต้องใช้คนอื่นเพื่อหลีกเลี่ยงคอขวด
- คนเก่งที่สุดไม่ควรถูกใส่ทุกงานจน Capacity เต็มทั้งโครงการ

### แบบฝึกก่อนวางแผน

ให้ทีมตอบ 3 คำถาม:

1. ใครมีโอกาสเป็น Bottleneck มากที่สุด?
2. งานใดต้องใช้ทักษะเฉพาะ?
3. ถ้าคนนั้นไม่ว่างหนึ่งวัน ใครหรือ Vendor ใดช่วยแทนได้?

## 5.3 Chaos — เห็นรายการงานก่อนจัดระบบ

หน้านี้จำลองสภาพที่หลายโครงการเริ่มต้นด้วยรายการงานจำนวนมาก แต่ยังไม่รู้ว่าอะไรสำคัญหรือเชื่อมโยงกันอย่างไร

### วิธีเล่น

1. อ่านการ์ดงานทั้งหมดอย่างรวดเร็ว
2. ลากหรือจัดรายการตามสัญชาตญาณของทีม
3. สังเกตว่าทีมใช้เกณฑ์อะไร เช่น งานที่เสียงดัง งานที่ใกล้ Deadline หรืองานของผู้บริหาร
4. เมื่อ Facilitator ให้หยุด ให้เตรียมตอบว่าเหตุใดทีมจึงเลือกทำสิ่งนั้นก่อน

### บทเรียนสำคัญ

ความเร่งด่วนไม่เท่ากับความสำคัญ และ Activity จำนวนมากไม่รับประกันว่า Mission จะสำเร็จ

## 5.4 Ask Sponsor — ใช้คำถามให้คุ้ม

ทีมมี Question Token จำกัด การบันทึก Q&A หนึ่งครั้งใช้หนึ่ง Token

### ขั้นตอน

1. เลือกประเด็นที่หากไม่รู้แล้วอาจทำให้ Goal, Scope, Plan หรืองบประมาณผิด
2. พิมพ์คำถามในช่อง Question
3. ถาม Facilitator ซึ่งรับบท Sponsor โดยตรง
4. บันทึกคำตอบในช่อง Sponsor Answer
5. จำแนกคำตอบเป็น **Fact**, **Assumption** หรือ **Unknown**
6. กด Save Q&A เพื่อใช้ Token และเก็บหลักฐาน

### ลำดับคำถามที่แนะนำ

ถามเรื่องที่เปลี่ยนการตัดสินใจมากที่สุดก่อน:

1. **Purpose และ Success** — ทำไปเพื่ออะไร และสำเร็จวัดจากอะไร
2. **Constraint** — วัน งบ คน สถานที่ หรือเงื่อนไขใดเปลี่ยนไม่ได้
3. **Must-have** — สิ่งใดจำเป็นต่อผลลัพธ์
4. **Approval และ Dependency** — ใครต้องอนุมัติอะไร ภายในเมื่อใด
5. **Preference** — สิ่งที่อยากได้แต่ต่อรองได้

### ตัวอย่างคำถามที่มีคุณภาพ

- “เมื่อจบงาน Sponsor จะใช้ตัวชี้วัดอะไรบอกว่างานสำเร็จ?”
- “ถ้าต้องเลือกระหว่างจำนวนผู้เข้าร่วมกับกิจกรรมเสริม อะไรสำคัญกว่า เพราะอะไร?”
- “เนื้อหาประเภทใดต้องได้รับอนุมัติก่อนเผยแพร่ และส่วนใดดำเนินการคู่ขนานได้?”

### คำถามที่ควรปรับ

แทนที่จะถาม “ควรทำ Task ไหนก่อน?” ให้ถาม “ผลลัพธ์หรือข้อจำกัดใดมีความสำคัญที่สุด?” เพราะทีมมีหน้าที่เปลี่ยน Requirement ให้เป็นแผนเอง

## 5.5 Goal & Scope — สร้าง Mission Definition

หน้านี้คือจุดที่ทีมเปลี่ยนข้อมูลกระจัดกระจายให้เป็นข้อตกลงร่วม

### Goal

Goal ที่ดีควรบอก:

- ผลลัพธ์ที่ต้องเกิด
- กลุ่มคนที่ได้รับผลลัพธ์
- เวลาและข้อจำกัดหลัก
- ตัวชี้วัดสำคัญ

ตัวอย่างโครงประโยค:

> ภายใน [วัน/เวลา] ทีมจะส่งมอบ [ผลลัพธ์] ให้ [ผู้มีส่วนได้ส่วนเสีย] โดยบรรลุ [ตัวชี้วัด] ภายใต้ [ข้อจำกัด]

### Success Measures

ใช้ตัวเลขหรือเงื่อนไขที่ตรวจได้ เช่น:

- จำนวนหรืออัตราการเข้าร่วม
- คะแนนความพึงพอใจ
- จำนวนผลลัพธ์ที่นำไปใช้ได้
- วันส่งมอบ
- วงเงินที่ได้รับอนุมัติ

### Scope

แยกให้ชัด:

- **In Scope** สิ่งที่ทีมรับผิดชอบ
- **Out of Scope** สิ่งที่ไม่รับผิดชอบ
- **Must-have** ถ้าขาดแล้ว Mission ไม่สำเร็จ
- **Nice-to-have** มีแล้วดี แต่ลดหรือยกเลิกได้เมื่อเกิด Trade-off

### Facts, Assumptions และ Constraints

- **Fact** ได้รับการยืนยันแล้ว
- **Assumption** ทีมเชื่อว่าเป็นจริงแต่ยังไม่มีหลักฐาน
- **Unknown** ยังไม่มีคำตอบและต้องติดตาม
- **Constraint** เงื่อนไขที่ทีมต้องทำงานอยู่ภายใน

### ขออนุมัติ Mission

เมื่อกรอกครบ ให้ทีมสรุป Goal, Success, Scope และข้อสมมติฐานแก่ Facilitator รับฟังผลว่า:

- Approved
- Conditional Approval
- Revise

บันทึกผลและเงื่อนไขในหน้า Player ด้วยตัวเอง การอนุมัติในหน้าของ Facilitator ไม่ได้ Sync มาที่ Player อัตโนมัติ

## 5.6 Priority — ตัดสินใจว่าจะให้ความสำคัญกับอะไร

ใช้ 4 ระดับ:

- **Must** จำเป็นต่อ Mission, Success Measure, Compliance หรือ Critical Dependency
- **Should** มีผลสูง แต่มีทางเลือกหรือเลื่อนได้บางส่วน
- **Could** มีคุณค่าแต่ไม่ควรเบียด Must/Should
- **Drop** ไม่ทำในแผนปัจจุบัน

### Priority มีผลอย่างไร

Priority ช่วย:

- เรียงงานใน Plan
- ชี้ว่า Capacity ควรไปอยู่ที่ไหนก่อน
- บอกว่างานใดเหมาะกับ Vendor
- ช่วยเลือกสิ่งที่จะลดเมื่อเงินหรือเวลาน้อยลง
- ทำให้ Facilitator เห็นเหตุผลของทีม

Priority **ไม่ได้**:

- จัดวันให้โดยอัตโนมัติ
- จองคนหรือ Vendor ให้โดยอัตโนมัติ
- ทำให้ Dependency หายไป
- รับประกันว่า Must ทุกงานจะทำเสร็จ หากแผนใช้ Capacity เกินจริง

### วิธีตัดสินใจ

ประเมินแต่ละ Task ด้วยคำถาม 5 ข้อ:

1. เชื่อมกับ Success Measure ใด?
2. ถ้าไม่ทำ ผลกระทบคืออะไร?
3. เป็น Dependency ของงานใด?
4. มี Deadline หรือ Approval ใด?
5. ทำเอง จ้าง หรือไม่ทำ ทางเลือกใดเหมาะที่สุด?

### การใช้ Delegate

ในเกมให้ตีความ Delegate เป็น “งานที่ควรส่งให้คนอื่นหรือ Vendor” ไม่ได้แปลว่างานไม่สำคัญ งาน Must ก็ Delegate ได้ หากการซื้อ Capacity หรือทักษะภายนอกช่วยรักษา Critical Path

## 5.7 Plan — วางงานลงคนและเวลา

หน้านี้เป็นหัวใจของ Project Planning

### ข้อมูลบนการ์ด Task

- **Effort / ต้องใช้** จำนวนชั่วโมงรวมของงาน
- **Allocated / จัดสรรแล้ว** ชั่วโมงที่ใส่ในแผนแล้ว
- **Remaining / เหลือ** ชั่วโมงที่ยังต้องวาง
- **Due By** วันล่าสุดที่ควรเสร็จ
- **Planned Finish** วันที่งานจะเสร็จตาม Allocation จริง
- **Skills** ทักษะที่เหมาะกับงาน
- **Dependencies** งานที่ต้องเสร็จก่อน
- **Priority** Must, Should, Could หรือ Drop

### วิธี Allocate

1. เลือก Task
2. เลือกคน
3. เลือกวัน
4. ใส่จำนวนชั่วโมง
5. ตรวจข้อมูล Selected Task และ Selected Resource
6. กด **Allocate / จัดสรร**

หลัง Allocate สำเร็จ ช่องชั่วโมงจะกลับเป็น 0 เพื่อป้องกันการกดซ้ำโดยไม่ตั้งใจ

ระบบคำนวณ Capacity จากรายการที่ Allocate แล้วเท่านั้น ตัวเลขที่กำลังพิมพ์แต่ยังไม่กดจะใช้สำหรับ Preview คำเตือน แต่ยังไม่ถือว่าอยู่ในแผน

### กฎ Capacity

แต่ละคนมี 6 ชั่วโมงต่อวัน:

- 0–4 ชั่วโมง: ยังมี Buffer
- มากกว่า 4 ถึง 6 ชั่วโมง: ใช้งานค่อนข้างแน่น
- มากกว่า 6 ชั่วโมง: Over Capacity และควรแก้

อย่าใช้ 6 ชั่วโมงเต็มทุกคนทุกวันโดยไม่จำเป็น เพราะเมื่อมีเหตุการณ์ใหม่ ทีมจะไม่มีที่ว่างให้ปรับตัว

### กฎ Dependency

ระบบดูจากวันที่งานต้นทาง “เสร็จตามแผนจริง” ไม่ได้ดูเพียง Due Date บนการ์ด

- ถ้างาน A เสร็จ Day 3 งาน B ที่ขึ้นกับ A เริ่ม Day 3 ได้ ถือว่าเป็น Same-day Handoff
- ถ้างาน A เสร็จ Day 2 แม้ Due By จะเป็น Day 3 งาน B เริ่ม Day 2 ได้
- ถ้างาน A ยังเหลือชั่วโมง งาน B ที่ขึ้นกับ A จะถูกเตือนหรือบล็อกตามลำดับจริง
- งานที่ไม่พึ่งกันสามารถทำพร้อมกันได้

ตัวอย่าง:

- เช้า: May ทำงาน A อีก 2 ชั่วโมงจนงานเสร็จ
- บ่าย: May หรือคนอื่นเริ่มงาน B ที่พึ่งงาน A ในวันเดียวกัน

ระบบใช้ระดับ “วัน” จึงถือว่าการส่งต่องานในวันเดียวกันทำได้ ทีมควรอธิบายลำดับเช้า–บ่ายให้ Facilitator ทราบหากเป็น Critical Handoff

### วิธีวางแผนที่แนะนำ

1. วาง Must ที่เป็น Dependency ต้นทางก่อน
2. วางงานที่มี Deadline เร็ว
3. วาง Critical Path ให้เห็นตั้งแต่ต้นจนถึง Day 10
4. กระจายงานจากคนที่เป็น Bottleneck
5. เก็บ Buffer ในวันสำคัญ
6. ตรวจ Remaining ของทุก Must
7. ตรวจ Planned Finish เทียบ Due By
8. พิจารณา Vendor เฉพาะจุดที่ช่วย Mission จริง

### ป้าย At Risk หมายถึงอะไร

งานอาจขึ้น At Risk แม้ Allocated ครบ หาก:

- Planned Finish ช้ากว่า Due By
- Dependency ยังไม่จบตามลำดับ
- มีการเปลี่ยนแปลงจาก Event
- แผนพึ่งทรัพยากรหรือเงื่อนไขที่มีความเสี่ยง

ถ้า Allocated ครบและ Planned Finish ไม่เกิน Due By แต่ยังขึ้น At Risk ให้ตรวจ Dependency และ Event ก่อน แล้วแจ้ง Facilitator หากข้อมูลไม่สอดคล้อง

## 5.8 Market — ใช้ Vendor อย่างมีกลยุทธ์

Vendor ไม่ใช่เพียง “ของซื้อเพิ่ม” แต่เป็นทางเลือกในการซื้อ:

- Capacity
- ทักษะเฉพาะ
- ความเร็ว
- การลดความเสี่ยง

### ก่อน Add to Plan

ถาม 4 ข้อ:

1. Vendor ช่วย Task หรือความเสี่ยงใด?
2. ถ้าไม่ซื้อ ทีมมี Capacity และทักษะพอหรือไม่?
3. Vendor ลดเวลาหรือลด Effort ของทีมอย่างไร?
4. เงินก้อนนี้มี Opportunity Cost กับ Must อื่นหรือไม่?

### สถานะ Vendor

- **Add to Plan** เป็นรายการที่กำลังพิจารณาและยังนำออกได้
- เมื่อ Commit Plan แล้ว Vendor ที่ยืนยันถือเป็น Commitment
- ถ้าต้องยกเลิกหลัง Commit ให้ใช้ Decision Request พร้อมเหตุผลและผลกระทบ

### อย่าทดลองกดโดยไม่อ่านผล

ดู Budget Panel ทุกครั้งหลังเพิ่ม Vendor ระบบจะแสดงค่า Task, ค่า Vendor, Planned Spend และ Remaining หรือ Over ทันที

## 5.9 Budget — อ่านเงินให้ถูก

คำหลักในระบบ:

- **Budget / Limit** วงเงินที่ได้รับอนุมัติในปัจจุบัน
- **Task Cost** ค่าใช้จ่ายของ Package ที่เลือกสำหรับ Task
- **Vendor Cost** ค่า Vendor ที่อยู่ในแผนหรือ Commit แล้ว
- **Planned Spend** ค่าใช้จ่ายตามแผนทั้งหมด
- **Remaining** เงินที่ยังเหลือเมื่อ Planned Spend ไม่เกิน Limit
- **Over** จำนวนเงินที่แผนเกิน Limit

สูตรพื้นฐาน:

`Planned Spend = Task Packages ที่ Included + Vendor ที่อยู่ในแผน/Commit`

`Remaining = Budget Limit - Planned Spend`

### Task Package

งานที่มีค่าใช้จ่ายอาจมีระดับ เช่น Full, Lean, Minimum หรือ Expanded แต่ละระดับมีต้นทุนและผลลัพธ์ต่างกัน

แนวทางเมื่อ Budget ลด:

1. ตรวจว่าแต่ละ Package ยังรองรับ Success Measure หรือไม่
2. ลดจาก Full เป็น Lean หรือ Minimum ก่อน หากผลลัพธ์หลักยังอยู่
3. เปลี่ยน Vendor หรือวิธีทำ
4. ลด Optional Scope
5. ยกเลิก Task เมื่อไม่มีทางเลือกที่คุ้มกว่า
6. ถ้ายังเกินและมีเหตุผลเชิง Mission ให้ส่ง Decision Request

### คำเตือนด้านจำนวนผู้เข้าร่วม

บาง Package มี Capacity รองรับผู้เข้าร่วม หากต่ำกว่า Forecast ระบบจะแจ้งเตือน ทีมต้องตัดสินใจว่า:

- จะรองรับ Forecast เต็มจำนวน
- จะยึดเกณฑ์ความสำเร็จขั้นต่ำที่ Sponsor ยืนยัน
- จะใช้แผนสำรองหรือวิธีควบคุมจำนวน

อย่าลดราคาอย่างเดียวโดยไม่บันทึกผลกระทบที่ยอมรับ

### แผนเกินงบทำได้หรือไม่

ระบบอนุญาตให้ทดลองวางแผนเกิน Budget เพื่อให้เห็น Trade-off แต่ไม่ควร Commit โดยไม่มีคำอธิบาย ทีมต้อง:

- ระบุเหตุผล
- อธิบายผลกระทบหากไม่อนุมัติ
- เสนอทางเลือก
- ส่ง Decision Request ถ้าต้องการวงเงินหรือข้อยกเว้นเพิ่มเติม

## 5.10 Control — ติดตามงานและสื่อสารสถานะ

การวางแผนว่าใช้ครบทุกชั่วโมงไม่ได้แปลว่างาน Done หน้านี้ใช้บันทึกสถานะการดำเนินงานจริง

### สถานะที่ควรใช้

- Not Started
- In Progress
- Blocked
- At Risk
- Done

### Status Update ที่ดี

ใช้โครงสร้าง 5 ส่วน:

1. **Status** ภาพรวมสั้น ๆ
2. **Top Issue** ความเสี่ยงหรือปัญหาสำคัญที่สุด
3. **Impact** กระทบ Goal, Success, เวลา หรืองบอย่างไร
4. **Action** ทีมทำอะไรอยู่
5. **Need** ต้องการการตัดสินใจหรือความช่วยเหลืออะไร

ตัวอย่าง:

> สถานะสีเหลือง งานหลักยังทัน Day 10 แต่ขั้น Approval มีเวลาสำรองเหลือน้อย หากช้ากว่าแผนจะกระทบงานสื่อสาร ทีมกำลังแยกส่วนที่ทำคู่ขนานได้ และต้องการคำตอบจาก Sponsor ภายในวันนี้

หลีกเลี่ยงรายงานแบบ Activity List เช่น “ทำโปสเตอร์แล้ว ประชุมแล้ว ติดต่อ Vendor แล้ว” โดยไม่บอกว่าผลลัพธ์หรือความเสี่ยงเปลี่ยนไปอย่างไร

## 5.11 Events — รับเหตุการณ์และ Replan

เมื่อ Facilitator ส่ง Event Code ให้ทีม:

1. พิมพ์รหัสในช่อง **Event Code / รหัสเหตุการณ์**
2. กด **Receive Event / รับเหตุการณ์**
3. อ่านเหตุการณ์ ผลกระทบ และ Current Event Impact
4. หยุดก่อนแก้แผน แล้วตอบว่าอะไรเปลี่ยน
5. บันทึก Team Response
6. กลับไปปรับ Goal, Priority, Plan, Market, Budget หรือ Control ตามความจำเป็น

### กรอบตอบ Event

ใช้ 6 คำถาม:

1. ข้อมูลใหม่คืออะไร?
2. Goal หรือ Success Measure เปลี่ยนหรือไม่?
3. Task หรือ Dependency ใดได้รับผล?
4. คน เวลา และ Budget เปลี่ยนอย่างไร?
5. ทีมจะ Stop, Start, Continue หรือ Change อะไร?
6. ต้องขอ Decision จาก Sponsor หรือไม่?

### สิ่งที่ Facilitator คาดว่าจะเห็น

- ทีมไม่ยึดติดกับแผนเดิมเพียงเพราะใช้เวลาเขียนมาแล้ว
- ทีมตัดสิ่งที่สำคัญน้อยกว่าเพื่อปกป้อง Mission
- ทีมดูผลกระทบข้าม Workstream ไม่แก้เฉพาะจุด
- ทีมบันทึกเหตุผล ไม่ใช่แค่เปลี่ยนตัวเลข

## 5.12 Decisions — ขอการตัดสินใจอย่างมืออาชีพ

ส่ง Decision Request เมื่อทีมแก้เองไม่ได้ภายใน Authority ที่มี เช่น:

- ต้องเพิ่มวงเงิน
- ต้องยอมรับการลด Scope หรือ Quality
- ต้องเปลี่ยน Constraint สำคัญ
- มีหลายทางเลือกที่กระทบ Sponsor ต่างกัน

### โครงสร้าง Decision Request

- **Situation** เกิดอะไรขึ้น
- **Recommendation** ทีมแนะนำอะไร
- **Impact** เวลา เงิน Scope คุณภาพ หรือความเสี่ยง
- **Decision Needed** ต้องการให้ตัดสินใจอะไร ภายในเมื่อใด
- **Alternatives** ทางเลือกอื่นและ Trade-off

ตัวอย่าง:

> จากข้อมูลล่าสุด แผนปัจจุบันเกินวงเงินและ Package ต่ำสุดจะไม่รองรับเป้าหมายที่ยืนยันแล้ว ทีมแนะนำลด Optional Scope สองรายการและคง Package งานหลักไว้ ผลคือประสบการณ์เสริมลดลงแต่ Success Measure หลักยังได้รับการปกป้อง ขออนุมัติการเปลี่ยน Scope ภายใน Day 6

หลักสำคัญคือ **Escalate with a recommendation** อย่าส่งเพียงปัญหาให้ Sponsor คิดแทนทั้งหมด

## 5.13 Final — สรุปผลและบทเรียน

ก่อนส่ง Final ให้ตรวจ:

- Goal และ Success Measure ยังตรงกับข้อมูลล่าสุดหรือไม่
- Must ทุกงานมีสถานะและ Owner ชัดหรือไม่
- Dependency สำคัญถูกจัดการหรือไม่
- Planned Spend อยู่ในวงเงินหรือมีการอนุมัติรองรับหรือไม่
- Risk ที่เหลือมี Owner และ Action หรือไม่
- Decision สำคัญมีหลักฐานหรือไม่

### Operational Result

ผลการส่งมอบอาจเป็น:

- Delivered
- Delivered at Risk
- Not Delivered

ผลการส่งมอบไม่ใช่ทั้งหมดของคะแนนการเรียนรู้ ทีมอาจเจอสถานการณ์หนักแต่แสดงการตัดสินใจและการสื่อสารที่ดีได้

### Export

กด Export เพื่อเก็บไฟล์ JSON เป็นหลักฐานหรือใช้ Import เล่นต่อ อย่าแก้โครงสร้างไฟล์ด้วยมือหากไม่จำเป็น

## 6. ตัวอย่าง Flow การทำงานหนึ่งรอบ

สมมติทีมพบว่า Task B ขึ้นกับ Task A:

1. ทีมจัด A เป็น Must เพราะเป็นต้นทางของงานอื่น
2. A ต้องใช้ 4 ชั่วโมง และ B ต้องใช้ 3 ชั่วโมง
3. Day 2 ช่วงเช้า ทีม Allocate A ให้ครบ 4 ชั่วโมง
4. ระบบคำนวณ Planned Finish ของ A เป็น Day 2
5. ทีมจึงเริ่ม B ใน Day 2 ได้แบบ Same-day Handoff
6. ทีมไม่ใช้คนเดิมเกิน 6 ชั่วโมง หากคนเดิมเหลือเพียง 2 ชั่วโมง ให้แบ่ง B 2 ชั่วโมงใน Day 2 และอีก 1 ชั่วโมงใน Day 3 หรือมอบให้คนอื่นที่เหมาะสม
7. ถ้ามี Event ทำให้คนหลักไม่ว่าง ทีมตรวจ Must ก่อน ย้าย Should/Could ออก แล้วพิจารณา Vendor
8. ถ้างบไม่พอ ทีมลดระดับ Package ที่ไม่กระทบ Success ก่อนตัด Must
9. ถ้ายังแก้ไม่ได้ ทีมส่ง Decision Request พร้อมข้อเสนอ

Flow นี้สะท้อนการคิดแบบโครงการจริง: ใช้ Priority ตัดสินใจ, ใช้ Plan ทดสอบความเป็นไปได้ และใช้ Status/Event ปรับแผนตามข้อมูลใหม่

## 7. ข้อผิดพลาดที่พบบ่อย

### “Must ทุกงาน”

ถ้าทุกอย่างเป็น Must ทีมจะไม่มีหลักคิดเมื่อ Capacity หรือ Budget ลด ควรผูก Must กับ Success, Constraint หรือ Critical Dependency เสมอ

### วางงานตาม Due Date เท่านั้น

Due Date บอกวันสุดท้าย ไม่ได้บอกวันเริ่ม ควรวางงานต้นทางให้เสร็จเร็วพอสำหรับงานถัดไป และทำงานที่ไม่พึ่งกันคู่ขนาน

### ใช้คนเก่งเต็ม 6 ชั่วโมงทุกวัน

แผนดูมีประสิทธิภาพแต่เปราะมาก เก็บ Buffer ให้คนที่เป็น Bottleneck

### ซื้อ Vendor เพราะมีเงิน

Vendor ควรแก้ Capacity, Skill หรือ Risk ที่ระบุได้ หากไม่มีผลต่อ Critical Path อาจเป็นค่าใช้จ่ายที่ไม่จำเป็น

### ลดงบโดยเลือก Package ถูกที่สุดทุกงาน

ต้นทุนลด แต่ Capacity หรือ Quality อาจต่ำกว่า Success Measure ต้องตรวจผลกระทบของ Package เป็นรายรายการ

### รายงานสิ่งที่ทำแทนสิ่งที่เสี่ยง

ผู้บริหารต้องการรู้ว่า Mission ยังปลอดภัยหรือไม่ ไม่ใช่เพียงจำนวนกิจกรรมที่ทีมทำ

### รอให้ปัญหาเกิดก่อน Escalate

เมื่อเห็นแนวโน้มกระทบ Deadline, Budget หรือ Success ให้แจ้งพร้อมข้อเสนอทันที

- [ ] Facts และ Assumptions แยกกัน
- [ ] Must เชื่อมกับ Success หรือ Constraint
- [ ] ทุก Must มี Owner และชั่วโมงครบ
- [ ] Planned Finish ไม่เกิน Due By
- [ ] Dependencies ทำตามลำดับจริง
- [ ] ไม่มีคนเกิน 6 ชั่วโมงต่อวัน
- [ ] มี Buffer ในจุดเสี่ยง
- [ ] Planned Spend และ Package Capacity เหมาะสม
- [ ] Vendor ทุกตัวมีเหตุผล

### หลังรับ Event

- [ ] ระบุว่าอะไรเปลี่ยน
- [ ] ตรวจ Goal และ Success
- [ ] ตรวจ Critical Path และ Dependency
- [ ] ตรวจ Capacity
- [ ] ตรวจ Budget และ Package
- [ ] ปรับ Priority หากจำเป็น
- [ ] บันทึก Team Response
- [ ] ส่ง Decision Request หากเกิน Authority

### ก่อน Final

- [ ] งานสำคัญมีสถานะจริง
- [ ] ปัญหาและความเสี่ยงถูกสื่อสาร
- [ ] Decision สำคัญมีเหตุผล
- [ ] ทีมอธิบาย Trade-off ได้
- [ ] Export ข้อมูลเรียบร้อย

## 9. หลักคิดที่นำกลับไปใช้ในงานจริง

- เริ่มจาก Outcome ไม่ใช่ Task List
- ถามเพื่อเปลี่ยนการตัดสินใจ ไม่ใช่ถามเพื่อเก็บข้อมูลให้ครบ
- Priority ต้องนำไปสู่การเลือกใช้เวลาและเงิน
- Schedule ที่ดีแสดง Dependency, Capacity และ Buffer
- Budget Cut ควรเริ่มจาก Value และ Package ไม่ใช่ตัดทุกอย่างเท่ากัน
- Status ที่ดีทำให้ผู้มีอำนาจตัดสินใจก่อนที่ปัญหาจะสายเกินไป
- แผนไม่ใช่คำสัญญาว่าทุกอย่างจะคงเดิม แต่เป็นฐานสำหรับการปรับตัวอย่างมีเหตุผล
